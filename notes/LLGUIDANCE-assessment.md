# llguidance vs xgrammar for sl (assessment, 2026-10-20; from memory of the llguidance README/design, NOT verified against the source here)
- Bounded-repeat blow-up: xgrammar 0.1.30 expands `{8,220}` into states and precomputes a token mask per state (80 s compile for our narration regex; we use `{n}` + unbounded tail). llguidance builds its lexer lazily from regex derivatives (derivre) and its Earley parser computes masks on demand, so large counted repeats should not explode. Likely a real win, but we only know it from the docs.
- "Narration must not contain X": derivre supports regex intersection (`&`) and negation (`~`) in the lark syntax, e.g. `/[^\n<]*/ & ~(/.*(Salzlake|Bankrott).*/)`. That is exactly the secret-term ban as a grammar constraint, inflections included via regex alternatives, instead of our exact token-sequence ban (which only matches the tokenizations we pre-generate).
- Swift integration: llguidance ships a C header (llguidance.h; matcher create / compute_mask / consume_token / rollback) and builds with cargo to a static lib. Needs a Rust toolchain in build.sh, a SwiftPM system-library or binary target, and a bridge replacing GrammarConstraint (mask is a bitmask like xgrammar's). Estimate 1-2 days incl. tokenizer plumbing. Our grammar is JSON-structural-tag today; it would have to be rewritten as lark (json_schema parts via llguidance's `%json`, which gm.py already used with llg).
- Gemma-4 tokenizer: llguidance reads HF tokenizer.json (toktrie_hf_tokenizers) and handles byte-fallback / SentencePiece-style vocabularies in general; Gemma-4's `<0xNN>` byte tokens and `<turn|>` EOS need a smoke test. The Python harness (gm.py) already ran Gemma via llg + lark successfully, which is good evidence it works for this model.
- Side finding (xgrammar): const_string with 2-byte UTF-8 compiled to wrong bytes (after "tr" only token <0xE0> was legal -> Tibetan glyph U+0FCB). Worked around by emitting non-ASCII literals as regex; llguidance would not have this problem class.
- Recommendation: not now. The ban + leak guard + regex workaround cover the observed failures. Revisit llguidance when (a) we want longer bounded sentences or (b) regex-level "must not contain" constraints, and budget the Swift FFI as its own task.
